# CRM на Payload — форк под «Вольницу»

## Зачем

Заказчику нужна не «просто админка текстов», а **рабочая CRM**:
- все заявки с сайта в одном месте;
- база клиентов;
- уведомления о новых заявках;
- фиксация истории и статусов;
- отметка прохождения маршрутов для ЛК.

**Решение:** Payload CMS (opensource) в составе Next.js-проекта. Форк/кастом под бизнес = свои коллекции, хуки, меню admin, без Bitrix/amocrm на этапе 1.

---

## Меню admin (логика для менеджера)

```
CRM
  ├─ Заявки          ← главная ежедневная вкладка
  ├─ Клиенты         ← база, карточка + история
  └─ Уведомления     ← лог Telegram/email

Контент сайта
  ├─ Маршруты
  ├─ Техника
  ├─ Тарифы
  ├─ Галерея
  ├─ FAQ
  └─ Настройки сайта (сезон, контакты, канал notify)

Операции
  └─ Прогресс маршрутов   ← «клиент прошёл трассу N»

Система
  ├─ Админы
  └─ Медиа
```

---

## Заявки (`leads`)

**Создание:** только с сайта (формы) или вручную менеджером.  
**Поля:** клиент, имя, телефон, дата/время желаемые, маршрут/тариф, комментарий, источник, статус, UTM/страница, timestamps.

**Статусы:**
`new` → `in_progress` → `confirmed` → `done`  
ветка: `cancelled` | `spam`

**Список:** сортировка по дате, фильтр по статусу/источнику/маршруту.  
**Карточка:** связь с Клиентом, кнопка «Повторить уведомление», заметки.

Все CTA сайта (`Забронировать`, выбор маршрута/тарифа, ночной квест, FAQ-контакты, бронь из ЛК) → **одна** коллекция `leads` с разным `source`.

---

## Клиенты (`customers`)

**Ключ:** телефон (нормализованный `+7…`).  
При новой заявке: найти клиента или создать → привязать lead.

**Карточка клиента:**
- контакты;
- список заявок;
- прогресс трасс (какие пройдены / какая открыта следующей);
- заметки менеджера.

Регистрация в ЛК: создаёт/связывает customer + account (email/password hash).

---

## Уведомления

**Globals `notify-settings`:**
- channel: `telegram` | `email`
- telegram bot token + chat_id **или** email to/from

**Хук** `leads.afterChange` (operation create):
1. Собрать текст: имя, телефон, маршрут, дата, источник.
2. Отправить в канал.
3. Записать `notifications` (success/fail).
4. Проставить `lead.notifiedAt`.

Вкладка «Уведомления» = аудит доставки (и отладка для приёмки US-04).

---

## Прогресс маршрутов (операции)

Менеджер после заезда:
1. Открывает клиента или «Прогресс маршрутов».
2. Ставит «Пройден: Зелёное озеро» (и т.д.).
3. Система открывает следующую трассу в ЛК.

Правило: [05-ROUTE-PROGRESS.md](./05-ROUTE-PROGRESS.md).

---

## Контент (CMS-часть того же Payload)

Менеджер меняет без разработчика:
- карточки маршрутов (цена, км, время, тексты, порядок);
- технику и сезон;
- тарифы;
- галерею и FAQ.

Публичный сайт читает те же коллекции (SSR / `revalidate`).

---

## Access control

| Роль | Права |
|------|--------|
| `admin` | всё |
| `manager` (если успеем в этапе) | CRM + контент + прогресс; без системных секретов |
| Публичный API | только create lead (через server action с валидацией); чтение контента |

Секреты notify и `PAYLOAD_SECRET` только в env.

---

## Приёмка CRM (чеклист US-04)

- [ ] Тестовая заявка с сайта видна во вкладке **Заявки**
- [ ] Клиент появился/обновился в **Клиенты**
- [ ] Уведомление ушло в выбранный канал; запись в **Уведомления**
- [ ] Админ меняет карточку техники/маршрут/сезон без кода
- [ ] Данные в PostgreSQL (не только «в памяти»)

---

## Граница этапа vs развитие форка

| Этап 1 (в договоре) | Потом (форк дальше) |
|---------------------|---------------------|
| Заявки + клиенты + notify + контент + прогресс | Воронка, задачи, напоминания |
| Один канал уведомлений | Мульти-менеджеры, смены |
| Базовые статусы | Аналитика, отчёты, экспорт |
| Payload admin UI | Кастомные view / white-label |

Онлайн-оплата, телефония, 1С — вне текущего приложения к договору.
